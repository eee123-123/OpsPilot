# OpsPilot Agent 工作规范

本文件对整个 `ops-pilot` 仓库生效。任何 Agent 在本仓库中分析、设计、编码、测试或编写文档时，都必须遵守本文件。

## 1. 每次会话必须读取的上下文

开始工作前，按顺序读取：

1. `AGENTS.md`；
2. `docs/system-design.md`；
3. `docs/implementation-plan.md`；
4. `docs/development-progress.md`；
5. 当前功能对应的 `docs/learning/Fxx-*.md`，如果已经存在。

先根据 `docs/development-progress.md` 确认当前功能、已完成工作、测试结果、阻塞项和下一步，不得在未检查进度记录的情况下重新开始或跳过未完成步骤。

## 2. 设计与范围约束

- `docs/system-design.md` 是产品范围和技术设计基线；
- `docs/implementation-plan.md` 是功能边界、依赖、排期和完成标准的事实来源；
- 只实现 F00～F17 及其需求编号覆盖的能力；
- 不以“预留接口”“以后补充”代替本版要求实现的功能；
- 实现需要偏离设计时，先更新系统设计和对应 ADR，再修改代码；
- 不得擅自增加 A2A、多租户、企业 SSO、Kafka、Kubernetes、移动端或任意 Skill 脚本执行；
- 不得删除测试、安全、审批、异常状态或可观测性要求来换取进度。

## 3. 工程实现规范

### 3.1 架构与模块边界

- 核心后端采用模块化单体，业务模块之间通过明确的应用服务、领域接口或领域事件协作；
- 禁止跨模块直接访问对方 Repository、内部实现类或私有数据表来绕过模块接口；
- 领域模型和核心业务规则不得依赖 Controller、数据库实现、模型厂商 SDK、MCP SDK 或前端类型；
- Model、Tool、MCP、存储和外部观测系统通过 Port/Adapter 隔离，Provider 差异不得泄漏到核心 Agent Runtime；
- Controller 只负责协议适配、参数校验和身份上下文，不承载业务编排；
- API 不直接暴露 JPA Entity，统一使用明确的 Request/Response DTO；
- 新增跨模块依赖前先检查方向是否符合系统架构；循环依赖不得通过延迟注入等方式掩盖；
- 时间、ID、随机数及外部结果等影响测试确定性的能力应通过可替换接口注入；
- 不创建只有转发作用的无意义抽象，也不以减少文件数量为由混合不同职责。

### 3.2 Java 与后端质量

- 使用 Java 21 和项目 Maven Wrapper，不依赖开发机全局 Maven 的特定版本；
- 遵守项目 Checkstyle 和 SpotBugs 规则；禁止通过全局排除或关闭规则掩盖新增问题；
- 异常必须保留业务语义和原始原因，不得使用空 `catch`、只打印堆栈或吞掉失败；
- 资源、线程池、HTTP 响应和流必须具有明确生命周期，并设置合理超时；
- 并发、重试和恢复逻辑必须说明幂等边界，不得默认“重复执行没有影响”；
- 核心代码注释解释设计原因、约束和不变量，不重复翻译代码表面含义；
- 合并前不得保留未实现占位、伪造返回值、仅用于演示通过的硬编码答案或无跟踪记录的 TODO/FIXME；
- Agent 生产代码不得读取评测标准答案或根据固定场景 ID 直接返回根因。

### 3.3 API 与数据规范

- 对外 API 使用 `/api/v1` 前缀，并保持 OpenAPI 与实际行为同步；
- 错误响应使用 RFC 9457 Problem Details，并包含稳定 `errorCode` 和 `requestId`；
- 所有响应传播 `X-Request-ID`；SSE 使用单调递增 `eventId` 并支持 `Last-Event-ID` 续传；
- 创建请求、Webhook、写工具和事件消费必须按设计实现幂等；
- 列表接口必须分页，不允许为方便前端直接加载无界数据；
- 所有数据库结构和初始化数据变更通过 Flyway 管理，禁止要求使用者手工执行 DDL；
- 已经进入 `main` 的 Flyway Migration 不得修改；任何变更使用新的版本迁移；
- 数据库约束、唯一键、索引和外键应与业务不变量一致，不能只依赖 Java 校验；
- 事务边界必须显式；领域状态与 Outbox Event 必须在同一事务提交；
- 数据迁移必须同时验证空库初始化和已有数据升级路径；破坏性迁移需要备份与恢复说明。

### 3.4 Agent、模型与工具安全

- 模型只负责受约束的推理，不拥有最终权限、审批权或任意代码执行能力；
- Tool、MCP、Skill、日志、知识文档和模型输出全部视为不可信输入，进入业务前必须校验；
- 暴露给模型的工具集合必须是用户权限、Skill 允许集合和 Policy 判定结果的交集；
- 所有写工具必须经过 Policy 和人工审批，并具有参数校验、幂等键、超时和审计记录；
- 不得让 Prompt、日志或 MCP 返回内容动态新增工具、扩大权限或绕过预算；
- Provider Adapter 必须归一化超时、限流、鉴权、工具调用和结构化输出异常；
- Agent Task 必须固定 Model、Prompt、Skill、Tool 和 Policy 版本快照；
- API Key、MCP Token、JWT 密钥及敏感原文不得写入代码、Git、前端、模型上下文或普通日志；
- 示例配置只提交无效占位值；真实密钥通过环境变量或本地未跟踪配置注入；
- 模型请求、工具参数和检索内容进入日志或 Trace 前必须脱敏和限长。

### 3.5 测试与验证纪律

- 测试必须覆盖正常路径、边界、权限拒绝、异常、重试、幂等和恢复；只验证 HTTP 200 不算业务验收；
- 默认自动化测试不得依赖公网、真实付费模型、执行顺序或本机已有数据库；
- 外部协议使用 WireMock/Fixture，数据库集成使用 Testcontainers；在线 Provider 只在显式 Smoke Profile 中运行；
- 时间和异步测试使用可控 Clock、轮询等待或事件同步，禁止用长时间固定 `sleep` 掩盖竞态；
- 修复缺陷时先增加能够复现问题的测试，再提交修复；
- 不得删除、禁用或放宽失败测试来获得绿色结果；不得使用 `skipTests` 作为完成证据；
- 后端核心模块 JaCoCo 行覆盖率不得低于系统设计规定的 80%，但不得用无断言测试刷覆盖率；
- 前端必须通过 TypeScript strict、ESLint 和相关组件测试；核心业务流程使用 Playwright 验证；
- 开发中先运行受影响模块测试；进入 `待合并` 前运行全部适用质量门禁和端到端验收；
- 每条“通过”结论必须来自本次实际执行的命令；未运行、环境阻塞和失败必须分别记录；
- 合并后至少执行构建和核心 Smoke Test，防止分支单独通过但集成失败。

### 3.6 前端交付规范

- 前端页面必须调用真实后端 API，不得以静态 Mock 页面代替最终交付；
- 每个页面覆盖加载、空数据、错误、无权限、会话过期和可恢复重试状态；
- 前端权限控制只负责交互体验，后端仍必须独立完成鉴权和授权；
- SSE 页面必须处理断线、续传、重复事件和组件卸载后的资源释放；
- 不使用无说明的 `any`、忽略 TypeScript 错误或关闭 lint 规则；
- 表单必须具有客户端提示和服务端校验反馈，危险操作必须展示影响和确认信息；
- 关键交互保证键盘可操作、标签可理解，并避免只依赖颜色表达状态。

### 3.7 可观测性与错误处理

- API、Agent Task、Agent Step、Model、Tool 和 MCP 调用通过 Request ID、Task ID 和 Trace ID 关联；
- 日志使用结构化字段，禁止在普通成功路径打印大段 Prompt、模型全文或工具原始返回；
- 指标名称和标签必须稳定；用户 ID、事故 ID、Prompt、错误全文等高基数字段不得作为 Metrics 标签；
- 外部依赖调用记录耗时、结果类别和受控错误码，同时避免泄露认证信息；
- 新增重试、熔断或降级时必须增加对应指标和测试，避免静默吞错；
- 用户可恢复错误、业务拒绝和系统故障必须使用不同错误码，不得统一返回模糊的“系统异常”。

### 3.8 依赖、配置与产物管理

- 新增依赖前先确认现有能力无法满足，并记录用途；禁止为了简单工具函数引入大型依赖；
- Java 和前端依赖版本集中管理，提交对应锁文件或 Maven 配置，保证构建可复现；
- 不随意执行大版本升级；升级必须单独说明兼容性影响并运行相关回归测试；
- 配置提供安全默认值并按环境分层；不得把个人绝对路径、端口临时修改或本机账号提交为默认配置；
- 构建产物、IDE 文件、日志、测试临时数据、备份文件和本地密钥必须进入 `.gitignore`；
- 提交前检查新增文件，防止密钥、数据库导出、模型输出样本或无关大文件进入 Git。

## 4. Git 分支与合并规范

除 F00 的仓库初始化步骤外，任何一级功能开发都必须先从最新 `main` 创建独立分支，不得直接在 `main` 上修改产品代码。

### 4.1 默认人工审查与合并

- 默认由 Agent 创建或继续使用功能分支，完成实现、测试、学习文档和分支内验收后停在 `待合并`；
- 除非用户在当次任务中明确授权，Agent 不执行 `git add`、`git commit`、`git push`、`git rebase` 或 `git merge`，也不创建或合并 Pull Request；
- Agent 交接时必须提供当前分支、变更摘要、实际测试证据、未完成事项和建议提交信息，供用户进行 Code Review；
- 默认由用户负责审查、暂存、提交和合并；用户在当次任务中明确授权时，Agent 可以执行这些 Git 操作。功能进入 `main` 后，必须执行合并后验证并将状态从 `待合并` 更新为 `已完成`；
- 未经验证不得臆造提交 ID、Pull Request 或合并结果；用户尚未合并时，功能最多标记为 `待合并`。

### 4.2 分支创建与合并条件

分支命名统一为：

```text
feature/fxx-short-module-name
```

例如：

- `feature/f00-engineering-foundation`；
- `feature/f08-model-gateway`；
- `feature/f09-agent-runtime`。

开始功能前必须执行并确认：

1. 检查工作区状态，识别并保留用户已有修改；
2. 确认 `main` 不包含未处理的产品代码修改；
3. 如果对应功能分支已经存在，继续使用原分支，不创建重复分支；
4. 如果分支不存在，从最新可用的 `main` 创建对应 `feature/fxx-*` 分支；
5. 在 `docs/development-progress.md` 和 Fxx 状态块中记录实际分支名；
6. 创建分支后才开始该功能的代码和状态修改。

F00 特殊规则：当前目录尚未成为 Git 仓库时，先初始化仓库，将设计、计划和 Agent 规范作为基线提交到 `main`，再创建 `feature/f00-engineering-foundation`。不得在未建立基线提交的情况下直接开始 F00 产品代码。

功能分支合并必须满足：

- 计划内代码已经实现；
- 规定的单元、集成、契约、端到端及验收测试已经通过；
- 学习文档已经生成并校验；
- `docs/learning/README.md` 已同步；
- 没有阻塞或高优先级未解决缺陷；
- 功能状态已经进入 `待合并`；
- 分支不存在意外文件或无关用户修改。

本地仓库使用 `--no-ff` 合并以保留一级功能边界。合并完成后在 `main` 上执行必要的构建或 Smoke Test，确认通过后把功能状态标记为 `已完成`。如果合并后验证失败，功能不得标记为完成，必须回到功能分支修复。

配置 GitHub 远程仓库后，默认流程为：推送功能分支、创建 Pull Request、等待规定检查通过、合并到 `main`。不得绕过失败检查，不得对共享分支 force push，不得未经确认删除远程分支。

提交和 Pull Request 规范：

- 提交保持单一目的，不把多个无关 Fxx 或格式化噪声混入同一提交；
- 使用 Conventional Commits，例如 `feat(f09): implement agent checkpoint recovery`；
- 常用类型为 `feat`、`fix`、`test`、`docs`、`refactor`、`chore`；
- 提交前检查 `git status`、暂存内容和 diff，确认不包含无关用户修改、敏感信息及生成产物；
- 已推送的共享提交不得擅自 amend、rebase 或 force push；
- Pull Request 必须说明 Fxx/需求编号、主要改动、测试证据、数据库或配置影响、风险与回滚方式；
- 涉及前端交互的 Pull Request 提供关键页面截图；涉及 Agent 链路的变更提供评测或 Trace 证据；
- 合并提交或 Pull Request 标题应能够独立说明该一级功能，不使用“update”“fix bug”等模糊描述。

功能合并到 `main` 后，必须在 `docs/development-progress.md` 记录分支名、提交或 Pull Request、合并结果和合并后验证结果，再切换到下一个 Fxx。

## 5. 功能状态管理

F00～F17 使用以下实施状态：

| 状态 | 含义 |
|---|---|
| `未开始` | 尚未进行该功能的实现 |
| `开发中` | 正在实现，代码尚未达到测试入口条件 |
| `待测试` | 计划内代码已实现，尚未完成规定测试 |
| `测试中` | 正在执行或修复该功能的测试 |
| `待修复` | 测试已发现问题，需要回到实现阶段 |
| `待文档` | 代码及规定测试已通过，学习文档尚未完成 |
| `待合并` | 代码、测试、学习文档和验收已通过，等待合并到 `main` |
| `已完成` | 功能已合并到 `main`，且合并后验证通过 |
| `阻塞` | 因明确的外部条件无法继续，已有可复现的阻塞证据 |

测试状态单独使用：`未执行`、`部分通过`、`通过`、`失败`或`不适用`。

状态转换原则：

```text
未开始 → 开发中 → 待测试 → 测试中 → 待文档 → 待合并 → 已完成
                         ↓
                       待修复 → 开发中

任一非完成状态可在具备明确证据时进入阻塞；阻塞解除后回到原工作状态。
```

开始一个一级功能前，必须先创建或切换到对应功能分支，再把 `docs/implementation-plan.md` 中该功能标题下的开发分支和实施状态更新为实际分支及 `开发中`，并同步更新 `docs/development-progress.md`。

每次发生以下情况时，必须立即更新两份进度记录：

- 开始开发；
- 完成计划内编码；
- 开始或结束测试；
- 测试失败或发现缺陷；
- 进入学习文档编写阶段；
- 准备合并；
- 合并完成或合并后验证失败；
- 功能完成；
- 出现或解除阻塞；
- 会话即将结束但功能尚未完成。

不得只在聊天消息中报告状态而不更新仓库文件。

## 6. 一级功能强制实施流程

实现或修改任意 Fxx 功能时，依次执行：

1. 确认 Fxx 编号、需求编号、依赖和验收条件；
2. 从 `main` 创建或继续对应的 `feature/fxx-*` 分支；
3. 记录实际分支名，将该功能标记为 `开发中`；
4. 完成后端、前端、数据库、权限、审计、可观测性等适用实现；
5. 编码结束后标记为 `待测试`；
6. 执行单元、集成、契约、端到端或其他规定测试，并记录真实命令与结果；
7. 测试失败时标记为 `待修复`，记录失败原因和下一步；
8. 规定测试通过后标记为 `待文档`；
9. 自动创建或更新对应的 `docs/learning/Fxx-*.md`；
10. 更新 `docs/learning/README.md`；
11. 重新校验代码、测试、学习文档和验收项的一致性；
12. 满足分支内全部验收条件后标记为 `待合并`；
13. 合并到 `main` 并执行合并后验证；
14. 合并和验证成功后标记为 `已完成`；
15. 更新 `docs/development-progress.md`，写明合并证据、下一功能或下一动作。

用户不需要另外要求生成学习文档或更新状态。这两项是每个一级功能的强制组成部分。

## 7. 学习文档强制要求

每个一级功能对应一份 `docs/learning/Fxx-<module-name>.md`。文档只能根据最终代码、数据迁移、页面和真实测试结果生成，不得根据计划推测实现。

每份学习文档至少包含：

1. 模块目标和业务价值；
2. 对应需求编号及验收条件；
3. 模块职责、边界及上下游关系；
4. 实际架构、核心流程或时序图；
5. 数据库表、API、后端类和前端页面导航；
6. 核心代码的分步讲解；
7. 实现难点和技术亮点；
8. 方案选择、替代方案与设计权衡；
9. Agent、MCP、Skill、RAG 或模型相关设计；
10. 权限、安全、幂等、异常和恢复机制；
11. 测试范围、执行命令和真实结果；
12. 常见问题与调试方法；
13. 面试问题和回答思路；
14. 可以独立完成的改造练习；
15. 基于真实实现的简历表达。

技术亮点必须回答：解决什么问题、为何选择当前方案、替代方案是什么、当前方案的代价是什么、代码在哪里、如何通过测试或运行证据证明。单纯引入依赖或调用框架 API 不算技术亮点。

## 8. 文档真实性与可验证性

- 不得引用不存在的文件、类、接口、配置、页面或数据库表；
- 所有代码位置使用仓库相对路径，必要时标注类名或方法名；
- 不得伪造测试结果、覆盖率、性能数据、模型效果或运行截图；
- Provider 没有真实密钥时，必须区分 Fixture 通过与在线 Smoke Test 通过；
- 不得把范围外能力或企业架构对应物描述为本地已实现；
- 后续修改模块行为时，必须同步更新对应学习文档；
- 学习文档必须让未参与开发的购买者能够独立理解和验证模块。

## 9. 跨会话交接要求

每次会话结束前，必须更新 `docs/development-progress.md`，至少记录：

- 当前 Fxx 和实施状态；
- 当前 Git 分支以及相对 `main` 的合并状态；
- 本次完成的工作；
- 修改的关键文件；
- 已执行的测试命令和结果；
- 尚未执行或失败的测试；
- 已知问题与阻塞；
- 下一步应执行的具体动作；
- 对应学习文档状态。

如果用户的新请求中断当前功能，也要先记录能够确认的实际进度；不得把未验证工作标记为完成。

## 10. 完成汇报要求

最终汇报一个 Fxx 功能时，必须说明：

- 完成的功能和需求编号；
- 主要代码文件；
- 测试命令及结果；
- 生成或更新的学习文档；
- 功能分支、合并提交或 Pull Request；
- 当前实施状态和下一步。

缺少规定测试、学习文档、合并记录或验收证据时，不得使用“已完成”。
