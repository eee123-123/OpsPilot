# OpsPilot Agent 工作规范

本文件对整个 `ops-pilot` 仓库生效。任何 Agent 在本仓库中分析、设计、编码、测试或编写文档时，都必须遵守本文件。

## 1. 每次会话必须读取的上下文

开始工作前，按顺序读取：

1. `AGENTS.md`；
2. `docs/system-design.md`；
3. `docs/implementation-plan.md`；
4. `docs/development-progress.md`；
5. 当前功能对应的 `docs/learning/Fxx-*.md`，如果已经存在。

先根据 `docs/development-progress.md` 确认当前功能、已完成工作、测试结果、阻塞项和下一步，不得在未检查进度记录的情况下重新开始或跳过未完成步骤。

## 2. 设计与范围约束

- `docs/system-design.md` 是产品范围和技术设计基线；
- `docs/implementation-plan.md` 是功能边界、依赖、排期和完成标准的事实来源；
- 只实现 F00～F17 及其需求编号覆盖的能力；
- 不以“预留接口”“以后补充”代替本版要求实现的功能；
- 实现需要偏离设计时，先更新系统设计和对应 ADR，再修改代码；
- 不得擅自增加 A2A、多租户、企业 SSO、Kafka、Kubernetes、移动端或任意 Skill 脚本执行；
- 不得删除测试、安全、审批、异常状态或可观测性要求来换取进度。

## 3. 功能状态管理

F00～F17 使用以下实施状态：

| 状态 | 含义 |
|---|---|
| `未开始` | 尚未进行该功能的实现 |
| `开发中` | 正在实现，代码尚未达到测试入口条件 |
| `待测试` | 计划内代码已实现，尚未完成规定测试 |
| `测试中` | 正在执行或修复该功能的测试 |
| `待修复` | 测试已发现问题，需要回到实现阶段 |
| `待文档` | 代码及规定测试已通过，学习文档尚未完成 |
| `已完成` | 代码、测试、学习文档和验收全部完成 |
| `阻塞` | 因明确的外部条件无法继续，已有可复现的阻塞证据 |

测试状态单独使用：`未执行`、`部分通过`、`通过`、`失败`或`不适用`。

状态转换原则：

```text
未开始 → 开发中 → 待测试 → 测试中 → 待文档 → 已完成
                         ↓
                       待修复 → 开发中

任一非完成状态可在具备明确证据时进入阻塞；阻塞解除后回到原工作状态。
```

开始一个一级功能前，必须把 `docs/implementation-plan.md` 中该功能标题下的实施状态更新为 `开发中`，并同步更新 `docs/development-progress.md`。

每次发生以下情况时，必须立即更新两份进度记录：

- 开始开发；
- 完成计划内编码；
- 开始或结束测试；
- 测试失败或发现缺陷；
- 进入学习文档编写阶段；
- 功能完成；
- 出现或解除阻塞；
- 会话即将结束但功能尚未完成。

不得只在聊天消息中报告状态而不更新仓库文件。

## 4. 一级功能强制实施流程

实现或修改任意 Fxx 功能时，依次执行：

1. 确认 Fxx 编号、需求编号、依赖和验收条件；
2. 将该功能标记为 `开发中`，记录本次工作目标；
3. 完成后端、前端、数据库、权限、审计、可观测性等适用实现；
4. 编码结束后标记为 `待测试`；
5. 执行单元、集成、契约、端到端或其他规定测试，并记录真实命令与结果；
6. 测试失败时标记为 `待修复`，记录失败原因和下一步；
7. 规定测试通过后标记为 `待文档`；
8. 自动创建或更新对应的 `docs/learning/Fxx-*.md`；
9. 更新 `docs/learning/README.md`；
10. 重新校验代码、测试、学习文档和验收项的一致性；
11. 全部满足 Definition of Done 后标记为 `已完成`；
12. 更新 `docs/development-progress.md`，写明下一功能或下一动作。

用户不需要另外要求生成学习文档或更新状态。这两项是每个一级功能的强制组成部分。

## 5. 学习文档强制要求

每个一级功能对应一份 `docs/learning/Fxx-<module-name>.md`。文档只能根据最终代码、数据迁移、页面和真实测试结果生成，不得根据计划推测实现。

每份学习文档至少包含：

1. 模块目标和业务价值；
2. 对应需求编号及验收条件；
3. 模块职责、边界及上下游关系；
4. 实际架构、核心流程或时序图；
5. 数据库表、API、后端类和前端页面导航；
6. 核心代码的分步讲解；
7. 实现难点和技术亮点；
8. 方案选择、替代方案与设计权衡；
9. Agent、MCP、Skill、RAG 或模型相关设计；
10. 权限、安全、幂等、异常和恢复机制；
11. 测试范围、执行命令和真实结果；
12. 常见问题与调试方法；
13. 面试问题和回答思路；
14. 可以独立完成的改造练习；
15. 基于真实实现的简历表达。

技术亮点必须回答：解决什么问题、为何选择当前方案、替代方案是什么、当前方案的代价是什么、代码在哪里、如何通过测试或运行证据证明。单纯引入依赖或调用框架 API 不算技术亮点。

## 6. 文档真实性与可验证性

- 不得引用不存在的文件、类、接口、配置、页面或数据库表；
- 所有代码位置使用仓库相对路径，必要时标注类名或方法名；
- 不得伪造测试结果、覆盖率、性能数据、模型效果或运行截图；
- Provider 没有真实密钥时，必须区分 Fixture 通过与在线 Smoke Test 通过；
- 不得把范围外能力或企业架构对应物描述为本地已实现；
- 后续修改模块行为时，必须同步更新对应学习文档；
- 学习文档必须让未参与开发的购买者能够独立理解和验证模块。

## 7. 跨会话交接要求

每次会话结束前，必须更新 `docs/development-progress.md`，至少记录：

- 当前 Fxx 和实施状态；
- 本次完成的工作；
- 修改的关键文件；
- 已执行的测试命令和结果；
- 尚未执行或失败的测试；
- 已知问题与阻塞；
- 下一步应执行的具体动作；
- 对应学习文档状态。

如果用户的新请求中断当前功能，也要先记录能够确认的实际进度；不得把未验证工作标记为完成。

## 8. 完成汇报要求

最终汇报一个 Fxx 功能时，必须说明：

- 完成的功能和需求编号；
- 主要代码文件；
- 测试命令及结果；
- 生成或更新的学习文档；
- 当前实施状态和下一步。

缺少规定测试、学习文档或验收证据时，不得使用“已完成”。
