# OpsPilot 项目介绍与学习价值说明

> 面向 Java 开发者的可运行 Agent 工程实战项目  
> 适用人群：校招、社招、Java 后端转 AI 应用开发、Agent 工程方向求职者  
> 项目形态：完整前后端产品 + Agent 工程底座 + 可复现故障场景 + 自动化测试与评测

## 发布使用说明

本文是 OpsPilot v1.0 完整交付版的对外介绍文案。对外发布前，项目必须通过系统设计文档中的全部验收项，并用真实运行截图、测试报告和实测数据替换文中的素材位置。不得在代码尚未交付或指标尚未测量时，对外宣称已经完成或达到对应指标。

OpsPilot 不承诺“购买即可拿到 Offer”，也不鼓励照背八股式项目话术。它提供的是一个能够运行、阅读、修改、测试和深入讲解的工程载体。最终面试表现仍取决于使用者是否真正理解并实践项目。

## 1. 一句话认识 OpsPilot

OpsPilot 是一个使用 Java 构建的智能故障诊断与应急处置平台：当示例微服务发生超时、错误率升高、数据库连接池耗尽或配置发布异常时，Agent 会收集日志、指标和调用链，生成诊断计划，调用工具验证根因，在执行高风险操作前等待人工审批，完成处置后验证恢复效果，并自动生成事故复盘。

它不是一个只会聊天的“大模型套壳页面”，而是一套包含状态、工具、权限、证据、审批、恢复、评测和可观测性的完整 Agent 产品。

## 2. 为什么选择这个项目作为简历主项目

许多 AI 项目停留在“输入一个问题，调用一次模型 API，再把答案显示出来”。这种项目容易上手，但面试官很难从中判断候选人的后端工程能力，也很难继续追问系统设计、可靠性和安全治理。

OpsPilot 选择“故障诊断与应急处置”作为业务背景，是因为这个场景天然要求 Agent 与真实系统交互：

- 不能只靠模型猜测，必须查询日志、指标、Trace 和变更记录；
- 不能让模型任意调用工具，必须控制权限、参数和调用预算；
- 不能让危险操作直接执行，必须经过策略判断和人工审批；
- 不能因进程重启丢失长任务，必须保存状态并支持恢复；
- 不能只展示一段最终答案，必须保留证据、步骤和审计轨迹；
- 不能凭主观感受判断 Agent 效果，必须有固定数据集和可重复评测。

因此，这个项目能够同时展示 Java 后端、全栈产品、Agent、工程治理和系统设计能力，适合作为 AI 应用开发或 Agent 工程岗位的核心项目。

## 3. 你会拿到一个什么样的产品

### 3.1 一条可以真正演示的业务闭环

以“数据库连接池耗尽”为例：

1. 在演示中心选择故障场景并注入故障；
2. 示例订单服务产生真实延迟、错误日志、指标和调用链；
3. 告警进入 OpsPilot，并聚合为一条事故；
4. Agent 根据事故上下文选择合适的 Skill；
5. Agent 制定诊断计划并逐步调用日志、指标、Trace 等工具；
6. Evidence Verifier 检查结论是否有足够证据；
7. Agent 提出回滚、限流或重启等处置建议；
8. Policy Engine 判断风险，高风险操作进入人工审批；
9. 审批通过后执行模拟处置，并再次查询指标验证恢复；
10. 系统生成包含时间线、根因、证据、操作和改进项的复盘报告；
11. 用户可以切换模型重跑同一场景，在评测中心比较效果。

这条链路可以从前端一直追踪到数据库、模型、工具、MCP 和可观测平台，而不是通过写死结果模拟一个漂亮页面。

### 3.2 完整的产品页面

项目包含真实可操作的前端，而不是只有 Swagger：

- 登录、用户和角色管理；
- 事故列表、事故详情和状态流转；
- 演示场景选择、故障注入和恢复；
- Agent 计划、步骤、证据和工具调用轨迹；
- 审批中心和操作确认；
- Skill、知识库、模型和系统配置管理；
- 站内通知和实时任务状态；
- 评测数据集、运行结果和版本对比；
- 审计记录、运行健康和数据导出；
- 加载、空数据、错误、无权限和断线重连状态。

### 3.3 可离线运行，也能连接真实模型

项目提供三类模型使用方式：

- Mock Model：不需要 API Key，适合学习、自动化测试和稳定演示；
- Ollama：使用本机部署的开源模型；
- 在线 Provider：接入 DeepSeek、通义千问、智谱 GLM、Kimi、豆包和 MiniMax；
- 通用 OpenAI-Compatible Adapter：用于兼容同类协议的其他模型服务。

没有模型密钥也能完成核心流程和测试；有密钥时可以进行真实连通性验证和同场景对比。

## 5. Agent 相关能力不是“贴标签”

### 5.1 受控 Agent Runtime

项目由 Java Runtime 掌握工作流，而不是把所有控制权交给模型。Runtime 负责：

- 创建 Agent Task 和 Agent Step；
- 驱动计划、推理、工具调用、验证和结束状态；
- 限制最大轮次、Token、耗时和工具调用次数；
- 在模型调用、工具调用和审批前后保存 Checkpoint；
- 通过任务租约避免多个 Worker 同时执行同一任务；
- 在进程异常退出后从安全位置恢复；
- 固定 Model、Prompt、Skill、Tool 和 Policy 版本快照。

购买者能够从这里理解：一个 Agent 工程的难点不只是 Prompt，而是如何把不确定的模型推理放进确定、可恢复、可治理的软件系统。

### 5.2 有明确职责的 Agent 协作

系统包含 Diagnosis Orchestrator 和 Evidence Verifier：

- Orchestrator 负责规划、选择工具、形成假设和推进诊断；
- Verifier 只允许使用只读工具，负责检查证据是否支持结论；
- Runtime 限制 Verifier 的追加轮次和权限，避免 Agent 之间无限讨论。

这不是为了展示“Agent 数量多”，而是通过职责分离解决诊断结论可信度问题。

### 5.3 真正的 MCP Client/Server

项目包含独立运行的 MCP Server 和主应用内的 MCP Client：

- 从 MCP Server 发现工具及 JSON Schema；
- 将 MCP 工具与本地 Java Tool 统一注册和调用；
- 对服务地址、工具名称和权限设置允许列表；
- 处理超时、协议异常、不可用和返回内容不可信等情况；
- 使用契约测试验证工具发现和调用；
- 至少一条完整诊断链路真实经过 MCP Client/Server；
- Trace 能从 API 跨越 Runtime 一直关联到 MCP 服务。

### 5.4 可版本化的 Agent Skill

Skill 不只是 Prompt 文件，而是一个受治理的能力包，包含：

- 适用场景和路由元数据；
- Prompt 与工作步骤；
- 允许使用的工具集合；
- 风险级别和预算；
- 知识库过滤条件；
- 输入输出约束；
- 版本、发布、撤回和回滚状态。

Runtime 会取 Skill、用户权限和 Policy 的交集，只有最终允许的工具才会暴露给模型。Skill 发生变更后，新任务使用新版本，已有任务继续使用启动时的快照，从而保证执行可复现。

### 5.5 Agent Eval，而不是“看起来回答得不错”

项目通过固定故障集评估不同模型、Prompt、Skill 和 Policy 版本，关注：

- 根因诊断正确率；
- 关键证据召回情况；
- 工具选择与参数正确性；
- 非法工具调用和审批绕过；
- 任务完成耗时；
- Token 与估算成本；
- 恢复验证结果；
- 不同版本之间是否发生能力回退。

确定性规则负责安全和工具行为评分，LLM-as-Judge 只作为辅助，避免让另一个模型决定所有评测结论。

## 6. 产品核心功能

### 6.1 事故与告警管理

- 告警 Webhook 接入、校验和幂等；
- 同类告警聚合为事故；
- 事故等级、负责人、时间线和状态流转；
- 失败诊断重试和人工接管；
- 事故详情与处置结果查询。

### 6.2 故障场景实验室

- 订单、库存、支付三个示例服务；
- 数据库连接池耗尽；
- 下游超时和异常；
- 慢查询；
- 配置发布错误；
- 错误率和延迟突增；
- 包含 Prompt Injection 内容的恶意日志；
- 故障恢复和演示数据重置。

### 6.3 工具与安全治理

- Tool Registry 和统一工具描述；
- 日志、指标、Trace、拓扑、变更和知识检索工具；
- 重启、回滚、限流等模拟写工具；
- 工具风险等级、参数校验和超时控制；
- 渐进式工具发现，减少无关 Schema 占用上下文；
- RBAC、Policy、审批和不可抵赖审计；
- API Key、MCP Token 和敏感日志脱敏。

### 6.4 多模型网关

- 多家国产模型统一调用接口；
- 流式响应、工具调用和结构化输出能力检测；
- 模型配置、启停、默认模型和备用模型管理；
- 超时、重试、限流、熔断和自动降级；
- Token、延迟、失败原因和估算成本记录；
- Provider Fixture 契约测试和在线 Smoke Test 分离。

### 6.5 RAG 知识库

- Runbook、历史事故和服务说明文档导入；
- 文档解析、切分、Embedding 和版本管理；
- PostgreSQL 全文检索与 pgvector 向量检索融合；
- 检索结果引用到诊断证据；
- Workspace、文档状态和标签过滤；
- 将知识内容视为不可信数据，防止文档中的指令扩大 Agent 权限。

### 6.6 审批、通知与审计

- 写操作强制进入人工审批；
- 审批人查看原因、参数、风险和证据；
- 通过、拒绝、超时和撤销；
- Agent 在等待审批时暂停，并在结果产生后继续执行；
- SSE 实时推送步骤、审批和任务结果；
- 站内通知、已读和未读状态；
- 关键操作审计查询和导出。

### 6.7 可观测与数据运维

- Agent Task、Step、模型、工具、MCP、审批和 Eval 指标；
- 结构化日志和统一 Request ID；
- API → Runtime → Model/Tool → MCP 跨服务 Trace；
- Provider、数据库、MCP 和示例服务健康状态；
- Grafana 指标看板和 Jaeger 链路查询；
- 配置管理、数据导出、备份、恢复和演示环境重置。

## 8. 它和常见项目有什么不同

| 对比维度 | 常见大模型项目 | OpsPilot |
|---|---|---|
| 业务形态 | 聊天页或单接口 Demo | 从告警到复盘的完整故障处置产品 |
| Agent 控制 | 模型自行循环或框架黑盒 | Java Runtime 显式状态机与预算控制 |
| 可靠性 | 失败后重新运行 | Checkpoint、任务租约、幂等和中断恢复 |
| 工具调用 | 几个写死函数 | Tool Registry、本地工具、MCP 和渐进式发现 |
| Agent Skill | Prompt 模板改名 | 带工具、预算、知识范围和生命周期的版本化能力包 |
| 模型支持 | 绑定一家国外模型 | 多家国产模型、Ollama、Mock 和通用适配器 |
| RAG | 上传 PDF 后问答 | 混合检索、引用、版本、范围过滤和注入防护 |
| 安全 | Prompt 中告诉模型不要违规 | RBAC、Policy、Approval、参数校验和审计硬约束 |
| 效果判断 | 手工提几个问题 | 固定故障集、Grader、版本对比和发布门禁 |
| 可观测性 | 打印模型返回值 | Agent、模型、工具、MCP 的 Metrics、Logs、Trace |
| 前端 | 简单对话框 | 事故、审批、Skill、知识、评测和系统管理控制台 |
| 测试 | 依赖真实 API，结果不稳定 | Mock、Fixture、集成测试、E2E 和在线 Smoke 分层 |
| 面试深度 | 主要讲 Prompt 和 API | 能讨论架构、可靠性、安全、治理、评测和权衡 |

## 9. 面试时可以深入讨论的问题

OpsPilot 的价值不在于堆技术名词，而在于每个技术选择背后都有可以追问的工程问题：

- 为什么核心后端选择模块化单体，而不是一开始拆成微服务？
- Agent 的状态机包含哪些状态，非法状态转换如何阻止？
- 为什么不能让模型直接决定是否执行写操作？
- 进程恰好在工具成功后、Checkpoint 前退出，如何避免重复副作用？
- Skill、Tool、Prompt、Policy 的版本为什么需要固定到任务快照？
- MCP Server 返回恶意内容时，系统如何维持原有权限边界？
- 多个模型都声称兼容 OpenAI 协议，为什么仍需要独立契约测试？
- RAG 检索到的 Runbook 为什么不能被当作系统指令？
- SSE 断线后如何从上次事件继续，而不是丢失执行过程？
- 为什么安全规则使用确定性判定，而不是全部交给 LLM-as-Judge？
- 为什么使用 PostgreSQL + pgvector，而不是引入更多中间件？
- 本地 Outbox、任务租约和 Policy 分别对应企业架构中的什么问题？

这些问题可以把面试从“调用过哪个模型”推进到“如何设计一个可信的 Agent 系统”。

以下内容只能在对应功能已实现、本人能够解释且有测试证据时使用：

> **OpsPilot——智能故障诊断与应急处置平台**  
> 使用 Java 21、Spring Boot、Spring AI、React、PostgreSQL/pgvector 构建完整 Agent 产品，实现告警聚合、证据驱动诊断、高风险审批、恢复验证和事故复盘闭环。设计显式 Agent Runtime，通过状态机、Checkpoint、任务租约、幂等和 Transactional Outbox 支持可靠执行与中断恢复；实现 MCP Client/Server、版本化 Skill、多国产模型网关、混合 RAG、Policy/RBAC 和 Agent Eval，并使用 OpenTelemetry、Prometheus、Grafana、Jaeger 建立端到端可观测链路。

量化数据必须从实际测试报告提取，例如：

- 固定评测集包含 `[实际数量]` 个场景，根因诊断准确率为 `[实测结果]`；
- 任务中断恢复测试覆盖 `[实际数量]` 个故障点，重复副作用次数为 `[实测结果]`；
- 工具选择准确率、P95 接口延迟和平均诊断耗时均填写真实测量值；
- 不得使用“提升 50%”“百万级并发”等没有基线和测试过程的数据。

## 12. 推荐学习方式

### 第一阶段：先把完整产品跑起来

- 使用 Mock Model 启动 Docker Compose；

- 跟踪 Agent Task 如何创建和进入状态机；
- 查看 Skill 路由、模型调用和工具筛选；

建议选择一个可验证的改造点，例如新增一种故障场景、接入一个模型 Provider、增加一个只读 MCP 工具或设计一个新的诊断 Skill，并同时补齐页面、测试、指标和文档。只有经过自主修改，项目才真正转化为自己的能力。

## 15. 常见问题

### Q1：这是一个聊天机器人项目吗？

不是。自然语言只是交互和推理的一部分，主体是事故领域、Agent Runtime、工具系统、审批、Skill、RAG、评测和可观测性组成的完整平台。

### Q2：不会 Python，可以学习吗？

可以。核心实现使用 Java 21 和 Spring Boot，前端使用 React + TypeScript。项目重点是 Java AI 应用与 Agent 工程，不要求用 Python 训练模型。

### Q3：必须有 DeepSeek 等模型的 API Key 吗？

不必须。Mock Model 可以运行完整演示和自动化测试。API Key 用于验证真实 Provider 和运行在线评测。

### Q4：需要单独安装 PostgreSQL、向量数据库和监控组件吗？

不需要。PostgreSQL + pgvector、Prometheus、Grafana 和 Jaeger 都通过 Docker Compose 启动。

### Q5：为什么没有直接使用 Kafka、Kubernetes 和微服务？

项目目标是在单机环境完整实现和验证 Agent 产品。模块化单体、Transactional Outbox、任务租约和清晰领域边界已经覆盖对应的工程问题，同时避免引入无法真实验证的复杂度。面试时可以解释企业架构的对应关系，但不会把未部署的组件包装成项目成果。

### Q6：可以直接把简历示例复制到自己的简历吗？

只有在你运行过项目、读懂实现、完成测试并能回答设计权衡时才应该使用。建议至少独立新增一个 Provider、Skill、工具或故障场景，并用自己的测试结果替换示例中的量化占位符。

### Q7：项目如何证明不是只能运行一次的 Demo？

项目提供 Mock、Fixture、自动化测试、固定评测集、备份恢复和演示数据重置能力。核心场景可以重复触发，Agent 过程可以通过数据库记录、审计、Metrics 和 Trace 交叉验证。

## 16. 这个项目真正希望解决的问题

OpsPilot 不只是帮助购买者在简历上多写几个技术名词。它希望提供一套足够完整的工程上下文，让你能够亲手理解：
