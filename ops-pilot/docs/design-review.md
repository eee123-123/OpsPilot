# OpsPilot 系统设计规范评审

> 评审对象：`docs/system-design.md` v1.0  
> 评审日期：2026-09-15  
> 评审结论：设计通过，可进入功能拆解与实现阶段  
> 适用边界：单机完整产品、求职项目、企业级工程思维展示

## 1. 评审口径

不存在所有公司统一使用的“大厂规范”。本评审采用大型软件团队常见的设计检查维度：

- 背景、目标、范围和非目标是否明确；
- 用户、场景、功能需求和验收是否闭环；
- 架构是否有清晰边界和关键决策记录；
- 数据一致性、可靠性、安全和权限是否可验证；
- Agent、模型、Skill、MCP 和 RAG 是否职责清晰；
- API、前端、部署、可观测性和数据运维是否构成完整产品；
- 测试、评测、质量门禁和复现方式是否明确；
- 本地已实现能力和企业对应关系是否诚实区分。

## 2. 总体结论

v1.0 在设计层面达到一个完整求职项目应具备的规范程度，并具备使用企业级工程思维进行面试讲解的基础。它不是企业生产系统，但不存在用“预留接口”代替产品实现的问题：设计文档中的功能全部进入实现和验收范围，范围外能力已明确排除。

该设计可以作为开发基线，原因包括：

- 92 条功能需求具有稳定编号；
- 前端、后端、数据库、MCP、示例服务和可观测组件均有明确运行入口；
- Agent 采用显式状态机、Checkpoint、预算和受控工具循环；
- Skill、Prompt、Tool、Policy 和 Model 使用版本快照保证可复现；
- 高风险操作通过 RBAC、Policy、审批、幂等和审计形成闭环；
- Mock Model 保证无密钥测试，Provider Fixture 和 Smoke Test 区分协议验证与真实账号验证；
- 功能测试、Agent Eval、安全测试、恢复测试、前端 E2E 和性能测试均有验收目标；
- 已记录关键 ADR，并解释了本地机制对应的企业问题。

## 4. 与企业工程实践的对应

本项目可以在面试中讨论企业级问题，但表述必须建立在已实现机制上：

| 已实现的本地机制 | 解决的问题 | 企业系统常见对应物 |
|---|---|---|
| PostgreSQL Checkpoint + 任务租约 | 长任务恢复、并发执行权 | Durable Workflow / 分布式调度 |
| Transactional Outbox + 本地发布器 | 状态与事件一致性 | Kafka/RabbitMQ 事件链路 |
| Spring Security + Policy + Approval | 最小权限和高风险控制 | IAM / 集中策略平台 |
| 文件型 Skill Registry + 版本快照 | 能力复用和变更治理 | 企业 Skill Registry |
| MCP Client/Server + 允许列表 | 工具协议和供应链边界 | MCP Gateway |
| Model Gateway + Provider 契约 | 多模型治理和避免锁定 | AI Gateway |
| Micrometer + OpenTelemetry | 指标、Trace 和故障定位 | 集中可观测平台 |
| 固定数据集 + Runtime Snapshot | AI 变更回归与可复现 | Eval Platform / 发布门禁 |

正确的面试表达是“我在本地用 X 机制解决了 Y，并验证了 Z；在企业系统中同一问题通常由 W 承载”。不能表述为已经部署 Kafka、Kubernetes、企业 IAM 或多租户平台。

## 5. 实施阶段最高风险

### 5.1 范围较大

完整产品包含后端、前端、Agent、六个在线 Provider、MCP、RAG、评测和可观测性。必须按依赖顺序完成，每个阶段保持可运行，禁止同时铺开大量未闭环模块。

### 5.2 多模型“支持”容易失真

没有对应 API Key 时只能证明协议 Fixture 兼容，不能证明真实账号可用。交付时必须分别展示：适配器实现状态、Fixture 契约结果、在线 Smoke Test 状态。

### 5.3 自研 Runtime 容易出现恢复缺陷

Checkpoint、审批暂停、工具幂等和任务租约是核心难点。实现时优先保证状态转换和恢复测试，再增加模型效果优化。

### 5.4 模拟故障可能过度理想化

示例服务必须实际产生请求、延迟、异常日志、指标和 Trace，Agent 不能直接读取预设答案。标准答案只允许进入评测模块。

### 5.5 前端容易沦为展示页

前端必须能够真正完成配置、触发、审批、重试、反馈、导出和管理操作，并覆盖错误、无权限及 SSE 重连状态。

## 6. 实现质量门禁

每个功能只有同时满足以下条件才算完成：

- 后端业务逻辑和 API 已实现；
- 对应前端入口或明确的系统入口已实现；
- 数据库迁移和初始化数据已实现；
- 权限、审计和可观测埋点已实现；
- 单元或集成测试已通过；
- OpenAPI、运行说明和验收步骤已更新；
- 不依赖人工修改数据库或源码才能演示；
- 不使用未测量的数字写入简历。

## 7. 评审结论

该设计符合项目级概要设计、产品需求和技术方案合并文档的常见规范，适合作为单人完整产品的开发基线。大型企业通常还会将 PRD、概要设计、详细设计、API、测试计划、安全评审和上线方案拆成独立文档；本项目采用合并设计文档加独立实现排期，规模与维护成本更匹配。

评审通过不代表代码质量已经得到证明。最终可信度由自动化测试、运行截图、Trace、评测报告、性能数据和演示视频共同建立。
